# iis-flexera

`iis-flexera` is a lightweight PowerShell-based observation tool for measuring the **IIS workload generated by a Flexera Inventory Beacon** over a representative period, typically seven days.

The project is intentionally focused on IIS. It is not intended to monitor the complete Flexera Beacon stack.

## Goal

The primary goal is to answer, with measured data rather than estimates:

- How much HTTP traffic does the Beacon handle?
- When are the IIS activity peaks?
- How much CPU and memory does the IIS worker process consume?
- Are requests ever queued or rejected by HTTP.sys?
- Which Flexera HTTP endpoints generate the most traffic?
- What are the response-time distributions (P50/P95/P99/max)?
- Are there HTTP errors or application-pool recycles during the observation window?
- Is the current IIS sizing appropriate for the observed workload?

The expected workflow is:

1. Deploy a PowerShell collector on a Flexera Inventory Beacon using IIS.
2. Run the collector for seven days by default.
3. Sample IIS and worker-process counters at a short interval (target: 15 seconds).
4. Parse IIS W3C logs for request-level statistics.
5. Produce machine-readable CSV/JSON data.
6. Generate a final summary report suitable for capacity analysis.

## Scope

### In scope

- IIS site/application discovery relevant to Flexera.
- Flexera IIS endpoints such as `ManageSoftRL` and `ManageSoftDL` when present.
- Application-pool discovery.
- Mapping IIS application pools to their current `w3wp.exe` PIDs.
- Handling worker-process PID changes after application-pool recycle.
- IIS performance counters.
- HTTP.sys request-queue counters.
- `w3wp.exe` CPU, memory, thread and handle metrics.
- IIS W3C log parsing.
- HTTP status-code distribution.
- Request-rate and bandwidth statistics.
- Request latency percentiles.
- Application-pool start/stop/recycle events.
- Seven-day unattended data collection.
- Final reporting and capacity-oriented summary statistics.

### Explicitly out of scope

The first version must **not** become a general Flexera monitoring agent. The following are excluded unless they are later required to explain IIS behavior:

- `BeaconEngine` monitoring.
- Flexera inventory jobs and import jobs.
- Oracle inventory collection.
- SQL/database monitoring.
- Flexera scheduled-task analysis.
- General server monitoring unrelated to IIS.
- Agent inventory processing outside the HTTP path.
- Prometheus, Grafana, Centreon, Nagios or other external monitoring integrations.

## Flexera/IIS context

A Flexera Inventory Beacon can use IIS to communicate with downstream devices or child beacons. Flexera documents, among others:

- `ManageSoftRL`: reporting/upload location.
- `ManageSoftDL`: download location.

The exact IIS topology must **not be hard-coded**. Depending on the Flexera deployment and Beacon role, sites, applications and application pools may differ.

The collector therefore needs to discover the IIS configuration and retain the discovered topology in its output metadata.

## Core measurements

The initial implementation should collect at least the following data.

### IIS / Web Service

- Current connections.
- Connection attempts per second.
- Requests per second or HTTP method request rates where available.
- Bytes received per second.
- Bytes sent per second.

### HTTP.sys request queues

- Current queue size.
- Rejected requests.
- Arrival rate where available.

### IIS worker process

For every `w3wp.exe` process associated with the monitored Flexera application pool(s):

- PID.
- CPU utilization.
- Working set.
- Private bytes.
- Thread count.
- Handle count.

PID-to-AppPool mapping must be refreshed automatically because IIS can recycle worker processes during the observation period.

### IIS W3C logs

The analyzer should use, when present:

- `date`
- `time`
- `s-sitename`
- `cs-method`
- `cs-uri-stem`
- `cs-uri-query`
- `sc-status`
- `sc-substatus`
- `sc-win32-status`
- `cs-bytes`
- `sc-bytes`
- `time-taken`

The implementation must read the `#Fields:` header instead of assuming a fixed column order.

## Default observation profile

Initial defaults:

- Observation duration: **7 days**.
- Performance-counter sampling interval: **15 seconds**.
- Output format: CSV for time series plus JSON for metadata and summary data.
- No external agent or database required.
- Administrative execution is acceptable for the first version.

All important defaults should eventually be configurable through PowerShell parameters.

## Expected output

A run should create a timestamped directory, for example:

```text
output/
└── 2026-08-26_081500/
    ├── metadata.json
    ├── iis-counters.csv
    ├── worker-processes.csv
    ├── apppool-events.csv
    ├── requests.csv            # optional normalized request data
    ├── summary.json
    └── report.md
```

The final report should include at least:

- Observation start/end/duration.
- Discovered IIS topology.
- Total requests.
- Average requests/sec.
- P50/P95/P99/max request rate.
- P50/P95/P99/max `time-taken`.
- HTTP 2xx/3xx/4xx/5xx distribution.
- Top endpoints by request count.
- Top endpoints by transferred bytes.
- Slowest endpoints by P95/P99 latency.
- `w3wp.exe` average/P95/max CPU.
- `w3wp.exe` average/P95/max private memory.
- Maximum connection count.
- Maximum HTTP.sys queue depth.
- Total rejected requests.
- Application-pool recycle/start/stop events.

## Design principles

1. **Read-only observation**: do not change IIS/Flexera configuration by default.
2. **Low overhead**: collection must be safe for a production Beacon.
3. **Automatic discovery**: avoid environment-specific names wherever possible.
4. **Recycle-safe**: follow worker-process PID changes automatically.
5. **Version tolerant**: avoid relying on a single Flexera version-specific layout.
6. **Raw data first**: preserve enough source data to rerun analysis without repeating the seven-day collection.
7. **Fail partially, not completely**: if one performance counter is unavailable, continue collecting the remaining data and record the limitation.
8. **No hidden dependencies**: PowerShell and Windows/IIS native interfaces should be sufficient for the first implementation.
